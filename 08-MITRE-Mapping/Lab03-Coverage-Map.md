# Lab 03 - Evidence-Scored Coverage Map vs. the SIEM's Own View

## Objective
Build the ATT&CK coverage map two ways and compare them:

1. **The SIEM's view** - every technique that produced at least one alert in the
   indexer. This is the data behind Wazuh's built-in MITRE ATT&CK dashboard, and
   what most coverage reports are screenshots of.
2. **The evidence view** - every technique scored by the best *live-test evidence*
   from [`detection-inventory.csv`](detection-inventory.csv) (Labs 01-02).

The gap between the two is the finding. A cell lit by an alert is not a cell
covered by a detection.

**No custom rule.** Output: two ATT&CK Navigator layers, a per-technique
comparison, and a tactic summary, all regenerated by one script.

## Step 1 - Extract the SIEM's view

One aggregation over every alert index, bucketing by technique and showing which
rules produced each:

```bash
C=/etc/wazuh-indexer/certs
sudo curl -s -k --cert $C/admin.pem --key $C/admin-key.pem \
  -H "Content-Type: application/json" \
  "https://localhost:9200/wazuh-alerts-*/_search" -d '{
    "size": 0, "track_total_hits": true,
    "aggs": { "t": { "terms": { "field": "rule.mitre.id", "size": 500 },
              "aggs": { "r": { "terms": { "field": "rule.id", "size": 8 } } } } } }'
```

The admin client certificate authenticates without the dashboard password. Result
exported to [`wazuh-alert-techniques.csv`](wazuh-alert-techniques.csv).

| Measure | Value |
|---|---|
| Alerts in the window | 380,938 |
| Alerts carrying any ATT&CK tag | 29,224 (**7.7%**) |
| Techniques with at least one alert | **64** |

## Results

### Headline: 64 lit vs. 32 proven
| | SIEM view | Evidence view |
|---|---|---|
| Techniques shown as covered | **64** | **32** (26 `fired` + 6 `fired-with-limit`) |
| Not deployed | - | 4 |
| Basis | an alert carried the tag | a live attack test produced the alert |

**Half of what the SIEM's own dashboard displays has never been tested here.**
Of the 64 lit techniques, 31 agree with the evidence; 3 are parent-ID duplicates;
2 are cells our own rule never covered; 28 come from shipped rules that fired on
whatever happened in the lab - never exercised by a deliberate attack.

### Finding - 100401 regressed when the environment changed
Rule 100401 (privileged logon, 4672) was verified in Module 04 Lab 02 on a Windows
11 workstation, where it fired once for the human admin and excluded service
identities. The alert view shows **8,062** alerts. Breaking them down:

| Agent | Account | Alerts |
|---|---|---|
| DC01 | `DC01$` (the DC's machine account) | 7,920 |
| DC01 | `Administrator` | 130 |
| windows | `vboxuser` | 8 |
| windows | `DWM-1` | 4 |

Alerts jump from ~1/week to **940 in the week DC01 was built** (Module 06) and stay
there. The exclusion list covers well-known service identities but not
`$`-suffixed machine accounts, which a domain controller produces constantly -
and `DWM-1` slipped through even on the workstation. **~98% of 100401's alerts are
false positives in the current lab.** The rule was correct when tested and broke
when a new asset type joined; nothing alerted on the rule itself degrading.
Status downgraded to `fired-with-limit`.

**Fix deployed.** The exclusion now also negates `$`-suffixed computer accounts
and the per-session `DWM-n` / `UMFD-n` identities:

```xml
<field name="win.eventdata.subjectUserName" negate="yes">^SYSTEM$|^LOCAL SERVICE$|^NETWORK SERVICE$|^DWM-\d+$|^UMFD-\d+$|\$$</field>
```

`\$$` means "ends in a literal `$`" - the same pattern already proven live in
Module 06's Kerberoasting rule 100600. Deployment was checked with a backup, a
`diff` showing exactly one changed line, matching md5 on both ends, and
`wazuh-analysisd -t` before restart.

Two things went wrong on the way, and both were caught before going live:

- The first `sed` over SSH matched nothing - quoting through two shells ate the
  pattern. The `diff` came back empty, which exposed it.
- The second attempt stripped the backslashes, producing `^DWM-d+$|...|$$`. A bare
  `$$` would match **every** username; under `negate` that silences the rule
  completely - trading 98% false positives for 100% false negatives. The syntax
  check **passed** on that broken line. Only reading the diff caught it. The fix
  was to write the line to a file and replace line 113 wholesale, so no escaping
  was involved.

**Offline replay is not a valid test here.** The 22 September archive holds 367
`DC01$` and 3 `Administrator` 4672 events. Replayed through `wazuh-logtest`, both
decode as generic JSON and **neither** reaches the Windows rule chain - including
the Administrator event that must alert. A tester that is silent on the positive
case proves nothing about the negative case. The live re-fire (an Administrator
logon on DC01 must still alert; `DC01$` must not) is carried to Lab 04.

### Finding - the SIEM claims a cell the lab proved is a gap
**T1021.001 (RDP)** is lit in the alert view with 6 alerts from shipped rule 92657
("Successful Remote Logon ... possible pass-the-hash"). No RDP session ever
occurred - the Windows 11 Home endpoint cannot host one (Module 04 Lab 02), and our
RDP rule 100412 is undeployed. An NTLM network-logon rule tagged with several
techniques lit the RDP cell. A dashboard reader would count Lateral Movement as
covered.

**T1087 (Account Discovery)** is lit by shipped 92031 (96 alerts, `net`-command
discovery on the endpoint). That may be genuine coverage of a *different*
procedure - but the procedure this lab actually tested, LDAP/BloodHound
enumeration against the DC, produced **no** detection (Module 06 Lab 04). A lit
technique cell says nothing about which procedures within it are covered.

### Finding - the evidence view lags the tags in one place
**T1095** (raw-TCP C2) is validated - 100302/100303 fired in Module 03 Lab 07 - but
has no alerts, because it was only added as a tag in Lab 02. Alerts carry the tags
that existed when they fired; a tag correction does not rewrite history. The alert
view is always a lagging, tag-at-the-time picture.

That is the input to Lab 05.

## Key findings
- **The SIEM's own ATT&CK view shows 64 techniques; 32 are proven.** Twenty-eight
  lit cells come from shipped rules never exercised by a deliberate attack.
- **Only 7.7% of alerts carry an ATT&CK tag,** and the most-alerted techniques are
  lit by routine activity (logons, registry churn, admin sudo). Alert volume is
  not a coverage metric.
- **A tuned rule regressed silently.** 100401 went from 1 alert to ~8,000 when a
  domain controller joined - 98% false positives, no signal that the rule had
  degraded.
- **Lit is not covered.** T1021.001 is lit by an NTLM-logon rule although no RDP
  ever happened; T1087 is lit by `net` discovery although the tested LDAP
  procedure is undetected.
- **The alert view lags tag corrections** (T1095 validated, zero alerts).
- **Coverage is host-centric.** Lateral Movement and Collection are empty;
  Exfiltration is shape-tested only.

## Result
Two Navigator layers and a 67-technique comparison, regenerated from the inventory
and one indexer query by [`build-layers.sh`](build-layers.sh). The evidence view
proves **32** techniques against the SIEM's **64** lit; the difference is
catalogued technique by technique. One regression found (100401), carried to
**Lab 04 - detection regression test**; tactic gaps (Lateral Movement, Collection,
Exfiltration) carried to **Lab 05 - threat-informed gap analysis**. **No custom
rule.**
